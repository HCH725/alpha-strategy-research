## Economic mechanism

### Source-reported

The artifact's `> Strategy Description` block (Chinese followed by an English `[trans]` rendering) reports, verbatim in substance:

- The strategy "generates trading signals by calculating exponential moving averages (EMAs) of different timeframes to form a fast EMA and slow EMA, and observing their golden crosses and death crosses", with "the fast EMA ... 12 days, while the slow EMA ... 26 days".
- Stated trading rules: "Enter long positions on golden cross of fast EMA crossing above slow EMA from below", "Enter short positions on death cross of fast EMA crossing below slow EMA from above", "Exit positions on divergence of the EMAs".
- The EMA formula is printed as `EMA(t) = (C(t) - EMA(t-1)) x SF + EMA(t-1)` where "SF is the smoothing factor"; no value of SF is given anywhere in the artifact (recorded contradiction 3's sibling gap, and the reason the prose formula alone cannot reconstruct the rule).
- Claimed advantages: clear logic, "relatively high win rate", effective noise filtering, applicability "across different instruments and timeframes", combinability, high capital efficiency. Claimed risks: failure in sharp selloffs, frequent false signals and whipsaws in ranges, parameter sensitivity, inability to locate reversal levels. Enhancement proposals: incorporate MACD, add trading volumes, combine with Bollinger Bands / candlestick patterns, and use LSTM to auto-tune the MA periods.
- None of these claims carries a sample, a metric, a baseline, a figure or a citation, so every one of them is recorded as a bare claim.

### Research interpretation

Read from the pinned code rather than from the prose: `MACD = EMA₁₂(close) − EMA₂₆(close)` is the raw difference of two exponential means of the daily close; `aMACD = EMA₉(MACD)` smooths that difference again; `delta = MACD − aMACD` is therefore the *difference of the difference*, i.e. a MACD-histogram-shaped quantity (the raw MACD line less its own 9-bar exponential mean). A sign change of `delta` is exactly the condition that the raw MACD line has just crossed its own signal line, which is a lagged, second-order statement about the change in the relative slope of a fast and a slow EMA of price.

Falsifiable mechanism hypothesis: on a 24/7 daily BTC series the 12/26 EMA difference of the close is persistent enough that its one-bar-to-bar acceleration, once smoothed by a 9-bar EMA, changes sign infrequently and in regimes where directional drift dominates; reading a sign flip of that acceleration as a change in the sign of the drift is a trend-following bet on continued autocorrelation of daily BTC returns after an EMA-smoothing lag, and the absence of any stop means the bet is held until the acceleration flips back. Candidate structural channels are herding and slow information diffusion in an asset with no closing auction, and the fact that the two EMAs are computed on `close` only, which makes the signal a pure function of the daily close path. This is a ported technical-analysis hypothesis: the source supplies no economic rationale and no evidence, so the mechanism is research interpretation, not source-reported fact.

## Signal

- Decision series: completed `1d` bars of the pinned instrument (the `period: 1d` value in the pinned backtest header).
- Inputs at decision bar `t`: `close[t]` and, through the `ta.crossover` / `ta.crossunder` prior-bar test, `delta[t−1]`. `open` is never read, `high`, `low` and `volume` are never read by any trading statement (the whole word `volume` occurs 0 times as a whole-word token in the artifact; the prose merely proposes "trading volumes" as a future enhancement).

Official first-party documentation states that when this parameter is true the broker emulator processes orders "on the closing tick of each bar", and adds "If the orders are market orders, the broker emulator executes them before the next bar's open." That is exactly a completed-bar decision with same-bar-close execution; there is no next-bar-open fill anywhere in the rule.
- Recalculation: `calc_on_every_tick = false` is written in the declaration, and `calc_on_order_fills` is absent (0 occurrences) so it takes its documented `false` default. Official documentation states that `calc_on_every_tick` "does not affect the strategy's executions on historical bars", so there is exactly one evaluation per completed bar and no intrabar re-evaluation can create a second order on the same bar.

The artifact has no `timestamp(`, no `time >=` comparison, no date input and no `timenow` (0 occurrences of each). `time`, `month(time)` and `year(time)` do occur, but only inside the returns/drawdown table block, where they bucket rows by calendar month and year for display; the resulting strings are written with `table.cell` and never reach `strategy.entry`. **Lookback, formulas and warmup**

- Parameters as declared: `fastLength = input(12)`, `slowlength = input(26)`, `MACDLength = input(9)`. The official `input(defval, title, ...)` signature makes the first positional argument the default value, so these are `defval` 12, 26 and 9 with no `minval`/`maxval` override; the artifact's `Strategy Arguments` table and the landing form both print 12, 26 and 9, i.e. no override. The other eight declared inputs (`Mode` default `Compound Equity`, `Return Precision` default 2, and six colour inputs) feed only the table and change no order.
- `MACD = ta.ema(close, fastLength) - ta.ema(close, slowlength)`, i.e. `ta.ema(close, 12) − ta.ema(close, 26)`.
  - Official `ta.ema`: "It calculates by using a formula: EMA = alpha * source + (1 - alpha) * EMA[1], where alpha = 2 / (length + 1)", and the same entry prints an equivalent implementation labelled "the same on pine": `pine_ema(src, length) => alpha = 2 / (length + 1)` with `sum := na(sum[1]) ? src : alpha * src + (1 - alpha) * nz(sum[1])`. That printed implementation fixes where the recursion starts: when the previous recursion value is `na` the current value is the current source value, so `ta.ema(close, 12)` and `ta.ema(close, 26)` are both defined on bar index 0 with value `close[0]`, and `alpha₁₂ = 2/13`, `alpha₂₆ = 2/27`. The entry's REMARKS sentence is quoted here in full — "na values in the source series are ignored; the function calculates on the length quantity of non-na values" — and is read as the `na`-handling rule the sentence opens with, because the entry itself supplies the seeding behaviour in the printed implementation rather than leaving it implicit. The v5→v6 migration guide records no change to `ta.ema` between v5 and v6 other than a type-qualifier fix for the `length` argument, so no second edition of the manual disagrees with this reading.
- `aMACD = ta.ema(MACD, MACDLength)`, i.e. `ta.ema(MACD, 9)` with `alpha₉ = 2/11`. `MACD[0]` is not `na`, so the same printed implementation seeds `aMACD[0] = MACD[0]`, and the series is defined from bar index 0.
- `delta = MACD - aMACD`, defined from bar index 0.
- Derived conditions, exact:
  - `longCondition[t] ⇔ delta[t] > 0 ∧ delta[t−1] ≤ 0`.
  - `shortCondition[t] ⇔ delta[t] < 0 ∧ delta[t−1] ≥ 0`.
  - These come straight from the reference definitions: `ta.crossover(source1, source2)` is true when "on the current bar, the value of source1 is greater than the value of source2, and on the previous bar, the value of source1 was less than or equal to the value of source2"; `ta.crossunder(source1, source2)` is the mirror image ("less than" now, "greater than or equal" before). Here `source2` is the constant `0`, so the tests reduce to the two signed conditions above. This record uses the v5 reference's wording as the governing definition because the pinned source is `//@version=5`; the v5→v6 migration guide records no semantic change for these functions and reproduces both in identical v5 and v6 example code.
- Warmup, derived from the pinned code and official documentation because the source declares none: `delta` first exists at bar index 0, and a boolean that is `na` cannot open an order (official v5→v6 migration guide: in v5 a value that must be boolean is evaluated so that `na` "is evaluated as false"), so the binding constraint is the prior-bar reference inside the cross functions. `ta.crossover(delta, 0)` and `ta.crossunder(delta, 0)` both need `delta[t]` and `delta[t−1]`, so **bar index 1, the close of the second completed `1d` bar, is the earliest possible entry**, and an exit can occur only after an entry. `max_bars_back` is not declared; official documentation states the required history buffer is detected automatically, and the rule references exactly one lag.
- Order of strategy calls within a bar: the long `if` block precedes the short `if` block, but the two conditions are mutually exclusive by construction — `delta[t] > 0 ∧ delta[t−1] ≤ 0` and `delta[t] < 0 ∧ delta[t−1] ≥ 0` cannot hold together, because they would require `delta[t]` to be simultaneously positive and negative. At most one order is created per bar and conflict priority is provably irrelevant.
- There is **no division anywhere in the trading rule**: the three indicator calls are `ta.ema` (multiplication and addition only, with a constant alpha), one subtraction chain, and two sign comparisons. The artifact does contain six `/` expressions, all six of them inside the returns/drawdown table block; see Execution assumptions for why they provably cannot reach an order.

**Entry**

- Long entry: `if (ta.crossover(delta, 0)) strategy.entry("MacdLE", strategy.long, comment = "MacdLE")`.
- Short entry: `if (ta.crossunder(delta, 0)) strategy.entry("MacdSE", strategy.short, comment = "MacdSE")`.
- The ids are the literal strings `MacdLE` and `MacdSE`. Their literal values cannot affect trades here: the rule contains 0 `strategy.close`, 0 `strategy.close_all`, 0 `strategy.exit`, 0 `strategy.order`, 0 `strategy.cancel`, 0 `strategy.cancel_all` and 0 `strategy.risk.*` call sites, i.e. no id-scoped command exists to address them. The `comment` argument is documented as display text that the Strategy Tester shows "instead of the automatically generated" identifier, so it is cosmetic.
- Both statements omit `qty`. Official reference: `qty` "The default is na, which means that the command uses the default_qty_type and default_qty_value parameters of the strategy declaration statement to determine the quantity" — here `strategy.percent_of_equity` with value `100`.
- Both statements omit `limit` and `stop`; official reference: `limit`/`stop` "The default is na, which means the resulting order is not of the limit or stop-limit type", so both are market orders.
- Direction: both sides explicit (one `strategy.entry` per side, `strategy.long` once and `strategy.short` once). Neither side is disabled.

**Exit**

- The pinned code contains exactly two order calls, both `strategy.entry`. Census over the whole 16,999-byte artifact after comment stripping: `strategy.close` 0, `strategy.close_all` 0, `strategy.exit` 0, `strategy.order` 0, `strategy.cancel` 0, `strategy.cancel_all` 0, `strategy.risk` 0, `limit =` 0, `stop =` 0.

Official documentation for `strategy.entry` states: "By default, when a strategy executes an order from this command in the opposite direction of the current market position, it reverses that position", with the worked example that a short order of 5 shares against an open long of 5 shares "triggers the sale of 10 shares to close the long position and open a new five-share short position". The same single same-bar-close fill performs the close and the new open.
- Stop loss: none. Take profit: none. Trailing stop: none. Time limit or maximum holding period: none. Flat state: reachable only before the first entry signal; after that the system is long or short until the opposite sign-cross. This directly contradicts the source's own "Exit positions on divergence of the EMAs" claim (recorded contradiction 2).

**Holding period, overlap and re-entry**

- Holding period: unbounded and determined entirely by waiting for the opposite sign-cross of `delta`; the source states no maximum or expected holding period.
- Maximum same-side concurrency: 1. `pyramiding` is not written in the declaration, so the value comes from the language default, and both official statements of that default describe the same observable rule even though they print different numbers: the v5 reference states "The maximum number of entries allowed in the same direction. If the value is 0, only one entry order in the same direction can be opened, and additional entry orders are rejected … The default is 0", while the v5 Strategies page states "The default value is 1, meaning the strategy can open new positions but cannot add to them using orders from strategy.entry() calls." Under each document's own definition of the parameter the result is identical — one open same-side entry, further same-side entries rejected — so the record records `pyramiding` as source-declared-by-language-default with that convergence stated rather than silently picking one number, and F3 forces the executing engine to confirm it.
- Same-direction re-entry: while a position is open, a same-side `strategy.entry` requires `delta` to leave the sign it is in and come back without an opposite cross ever firing. The only path is an exact zero-touch — `delta` falls from positive to exactly `0` (at which point `ta.crossunder` does not fire, because it requires `delta[t] < 0` strictly) and then rises again, so a second `ta.crossover` fires while the long is still open. In that case the documented default above rejects the add, so the position size still does not change. Everywhere else the opposite cross fires first and reverses the position.
- Cooldown: none declared, and Pine's v5 strategy declaration exposes no cooldown field. Because a fresh entry requires a fresh sign-cross event and the only competing event while a position is open is the opposite sign-cross, cooldown semantics are provably irrelevant rather than missing. The engine's separate "Order execution delay" setting is a user override whose default is 0 ticks, i.e. no delay.
